# QAI scenario format

This document defines the format tests are written in. It is the most
structural decision in the product: once customers have written scenarios, the
format cannot change without breaking their work.

## The core idea: separate intent from resolution

A QAI test is made of **two files of different natures**. This separation is
what makes both web/mobile portability and the cost model possible.

**The scenario** (`*.qai.yaml`) describes *what the user wants to do*. It is
written by a human or generated by the agent, versioned in git, reviewed in
code review. It **never** contains a CSS selector, an XPath, a technical id,
or a coordinate. It is platform-independent.

**The resolution** (`.qai/resolutions/<scenario>.<platform>.json`) describes
*how that intent was satisfied last time, on that platform*. It is produced by
the machine, versioned too, but regenerable and disposable.

```
checkout-guest.qai.yaml          ← one intent
  └── checkout-guest.web.json    ← its resolution on the web
  └── checkout-guest.ios.json    ← its resolution on iOS
  └── checkout-guest.android.json
```

Three direct consequences:

1. **Mobile port without a rewrite.** Supporting a mobile app means generating
   a new resolution file, not rewriting the tests. This is the product
   differentiator.

2. **Zero execution cost in the nominal case.** The resolution contains
   everything needed to replay the journey without calling a model. The model
   only runs at creation and on breakage.

3. **Auditable repair.** Because the resolution is versioned, a self-repair
   shows up as a git diff in the pull request. The customer sees exactly what
   the agent changed instead of trusting a black box.

## Anatomy of a scenario

```yaml
id: checkout-guest
title: Un visiteur non connecté peut commander un article
tags: [critical-path, revenue]

given:
  fixtures: [catalogue-standard]
  state: visiteur-anonyme

steps:
  - id: s1
    do: ouvrir la page d'accueil de la boutique

  - id: s2
    do: rechercher "chaise de bureau"
    expect: la liste de résultats contient au moins un article

  - id: s3
    do: ouvrir le premier article de la liste
    capture:
      article: le nom de l'article
      prix: le prix affiché

  - id: s4
    do: ajouter l'article au panier
    expect: l'indicateur du panier affiche 1 article

  - id: s5
    do: ouvrir le panier
    expect:
      - le panier contient "{{article}}"
      - le total est égal à {{prix}}
```

### English keys, content in the team's language

The structure (`id`, `do`, `expect`) is English by convention. Step bodies are
natural language, in **whatever language the team already uses**. A
French-speaking team writes its scenarios in French with no loss: the model
interprets the intent, not a parser. A direct advantage over the American
tools on the market, which all assume English.

### `id` — the resolution's anchor

Each step carries a stable identifier, assigned at creation. It **never**
changes, even if the step text is reworded.

This is subtle but critical: if steps were identified by position, inserting
one mid-journey would invalidate the cache of every step after it, and a
thirty-step scenario would cost a full resolve on every edit. Stable ids make
the cost of a change proportional to the change.

### `capture` — don't freeze data

`capture` extracts a value from the screen and exposes it to later steps as
`{{name}}`. It lets assertions mean something ("the total equals the price
seen on the product page") instead of constants that break on the first
catalog change.

### `given` — the starting state

A scenario does not build its own context by clicking through the app: it
declares the state it needs. `fixtures` are named data sets, defined elsewhere
and environment-specific. State setup is the hidden cost of end-to-end
testing; treating it as a first-class citizen avoids the field's most common
debt.

## Platform divergence

The format aims for portability by default, but some journeys genuinely
diverge — hover does not exist on mobile, a one-page web checkout may span
three screens in the app. Without an escape hatch, the portability promise
breaks on first contact with reality and teams abandon the format.

Two mechanisms, both **explicit and visible in review**:

```yaml
  # Refine a step per platform while keeping a shared intent
  - id: s5
    do: ouvrir le panier
    per_platform:
      web: cliquer sur l'icône panier dans l'en-tête
      mobile: ouvrir l'onglet Panier de la barre de navigation

  # Restrict a step to certain platforms
  - id: s7
    do: survoler la vignette pour afficher l'aperçu rapide
    only: [web]
```

The design rule: bare `do` is the normal case; `per_platform` and `only` are
exceptions you should be able to count. A scenario riddled with them means the
two apps have genuinely different journeys and need two scenarios — make that
visible rather than disguising it.

> **Never rename `per_platform` to `on`.** It is tempting, shorter, and breaks
> everything: YAML 1.1 — implemented by PyYAML and many parsers — parses the
> key `on` as the boolean `true`. The divergence block would vanish silently,
> with no error, and mobile scenarios would fall back to the generic intent
> unnoticed. For the same reason, `yes`, `no`, `off`, `y`, and `n` are banned
> as format keys.

## The repair safety boundary

This rule protects the product's credibility and is non-negotiable:

> **A repair may change *how* an element is reached.
> It may never change *what is asserted* about it.**

If step `s4` fails because the cart badge moved, the agent may find it again.
If it finds it showing `0`, that is a **failure**, not a repair. A self-repair
system allowed to touch assertions no longer detects regressions: it learns to
let bugs pass.

Three guardrails complete the rule:

- **A repair is bounded.** Past a set number of repaired steps in a single
  run, execution stops and escalates to a human. Massive drift means the
  application changed nature, not that the test went stale.
- **A repair cannot delete a step.** Bypassing a step that no longer passes is
  precisely the definition of a false negative.
- **A repair is a diff.** It rewrites the resolution file with the reason
  attached (`healNote`), and that diff is what goes to review. No one has to
  take the agent's word for it.

## The three execution tiers

The format is designed so each tier works without rewriting it:

| Tier | Trigger | Model cost | Expected frequency |
|---|---|---|---|
| Deterministic replay | resolution present and valid | none | ~95% of runs |
| Repair | a step fails to resolve | proportional to the breakage | on every UI change |
| Resolving (agentic exploration) | scenario creation, discovery | high | rare, high-value |

This distribution is what makes self-serve pricing viable where competitors
failed on infrastructure costs.

## What the format deliberately lacks

- **No loops, no conditionals.** A scenario is a linear journey. Needing logic
  means you are writing a program, and a bad one. Two scenarios beat one `if`.
- **No selectors, not even as an escape hatch.** Allowing `selector:` "just
  for hard cases" would kill mobile portability: the field would be used
  everywhere within six months. Hard cases belong in the resolution layer, not
  in the intent.
- **No technical assertions** (HTTP codes, database contents) in a UI
  scenario. That will come, but as a distinct test type.
